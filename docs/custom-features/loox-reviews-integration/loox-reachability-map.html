The Loox Reachability Map

What the Loox reviews app will and will not hand to a Shopify theme — and how to decide, on day one, whether a client’s review design is buildable at all.

The one thing to know

Loox gives a theme aggregate numbers for free, and individual review content only through a paid-tier API. Every Loox widget that renders review content does so inside a cross-origin iframe, so none of it can be restyled with CSS — not with !important, not with a scoped override, not at all.

So when a client hands you a custom review-card design, the question is never “how do we style the widget?” It is “which Loox plan are they on?” — and that decides whether the design is achievable before you write a line of Liquid.

What Loox actually exposes

Verified against a live store. “Reachable” means a theme can read the value in Liquid and render it in its own markup.

The iframe wall

This is the fact that kills most “just restyle the widget” plans. Worth checking on day one of any Loox project.

Renders in your DOM — styleable

  • Star rating widget · .loox-rating
  • Trust badge · .loox-trust-badge-widget

Renders in an iframe — sealed

  • Reviews widget · #looxReviews
  • Cards carousel
  • Testimonial carousel
  • Gallery carousel

How to check in ten seconds. Open the client’s live product page, inspect the reviews block, and look for an <iframe>. If the review content sits inside one, its appearance is fixed and no amount of theme CSS will change it.

The carousel’s entire styling surface

The v2 carousels are configured by data-* attributes on a .loox-v2-carousel-container div, which the Loox script turns into iframe query parameters. This list is exhaustive — if a design needs anything not on it, the widget cannot deliver it:

slideType · maxWidth · borderRadius · itemsPerView · mobileItemsPerView · imageRatio · maxNumberOfCharacters · desktopFontSize · mobileFontSize · reviewerNameColor · textColor · itemBackgroundColor · starsColor · starsBackgroundColor · arrows[backgroundColor] · arrows[iconColor] · arrows[hideOnMobile] · shadow · border[active] · border[width] · border[color] · pagination[active] · pagination[dotColor] · pagination[selectedDotColor] · autoplay[active] · autoplay[duration] · quoteMarkIcon · quotesIconColor · productIds

Colours and sizes only. No control over card layout, element order, or which fields appear. Two further limits worth knowing: the Cards and Gallery carousels hide text-only reviews entirely, and they show the customer’s photo, never the product image — which is what most custom designs actually ask for.

Three routes, and how to choose

Once you know the plan, the choice makes itself.

01

Storefront API into your own markup Best result

Fetch reviews client-side and render them in the design’s real HTML. Automatic and pixel-accurate — the only route that is both. The API returns the product’s name, URL and image, so cards showing a product photo work exactly as drawn.

Needs Convert or UnlimitedDesign fidelity fullUpdates automatic
02

Drop in the Loox widget

Use the app block as-is. Reviews stay current with no plan change, but you inherit Loox’s card layout and only its colour settings. Sound choice when the client has no strong design, or as an interim.

Needs any planDesign fidelity lowUpdates automatic
03

Curated cards in the theme editor

Build the section properly and let the merchant pick which reviews to feature. Matches the design exactly and costs nothing, but someone maintains it by hand. Pair it with the live aggregate badge so at least the headline number stays true.

Needs any planDesign fidelity fullUpdates manual

Build routes 1 and 3 as the same section. Identical markup, identical CSS — only the data source differs. That way a plan upgrade is a change of data source, not a rebuild, and shipping route 3 first costs nothing if the client later upgrades.

Two things to settle with the client before building

Which reviews surface. A store with hundreds of reviews and a design showing four needs a rule: newest first, 5-star only, photo-only, or per-product. The design will not tell you — ask.

What renders before the fetch resolves. A client-side fetch means the cards are empty on first paint. Decide between a skeleton, a small set of server-rendered fallback cards, or reserving the height — and remember review text fetched client-side is invisible to search engines.

Gotchas worth carrying forward

Each of these cost real time once. None are Loox-specific except the first.

Loox’s own reply will describe aggregates as “reviews”

First-line support answers “can we render review content?” with “yes — Loox stores a copy of each product’s reviews in metafields”, then lists reviews.rating and reviews.rating_count. Those are a score and a count. Quote the specific fields you need back at them; the second reply is usually accurate.

A 401 that ignores the store id means entitlement, not a typo

Send a deliberately invalid store id. If it returns the same 401 as your real one, the request is being rejected before the id is read — so the problem is plan access, not the identifier. Worth doing before asking support, because it turns a vague question into a specific one.

Figma star icons often export upside-down

Figma applies scaleY(-1) at the node, which the exported path does not carry. Paste it verbatim and the star renders with two points up. Check the geometry: a correct five-point star has one vertex at the top. Wrap the path in transform="matrix(1 0 0 -1 0 H)".

Swiper’s auto margins cancel flex stretching

The .swiper class sets margin-left: auto; margin-right: auto. Inside a flex column, an auto cross-axis margin stops the item stretching, so it collapses to its content width and overflows the page. Pin margin-inline-start: 0 when using a negative end margin for a full-bleed rail.

Shopify range settings cap at 101 steps

(max - min) / step must be 101 or fewer, or the theme fails to upload. Theme Check does not catch it — only the upload does. Also confirm the default is divisible by the step, or it silently snaps.

Shopify JSON files carry a comment banner

Every templates/*.json and locales/*.json opens with a /* ... */ block, so a plain JSON parser fails. Strip it to read, re-attach it to write. Round-trip the untouched file first to confirm your serializer matches the existing formatting — otherwise a one-line edit reformats thousands.
